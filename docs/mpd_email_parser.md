# MPD LISTSERV email parser — bug history & format quirks

This is the running log of every parser surprise we've hit while ingesting
MPD's daily Preliminary Crime / Arrest Report emails through Resend
Inbound. Treat it as the field guide next time the parser breaks: chances
are MPD has tweaked something subtle in the email template again.

The parser lives in `src/wswdy/email_reports.py`. The Resend webhook in
`src/wswdy/routes/inbound_webhook.py` calls into it for every
`email.received` event.

---

## What MPD sends — the canonical structure

A daily email from `mpd@subscriptions.dc.gov` (delivered via GovDelivery)
with subject `MPD: Preliminary <Crime|Arrest> Report for <ND>` where
`<ND>` is `1D`..`7D`.

The body is multipart: HTML and plain text. We always parse the **plain
text** part — it's far cleaner than the HTML, which is `<table>`-soup
generated by GovDelivery's templating.

The text body has, in order:

1. **Forwarded preamble** (when subscribers forward to us by hand) — `From:` / `Date:` / `Subject:` / `To:` lines.
2. **Image alt-text** — e.g. `[image: MPD Crime Blotter - 2D (Second District) Header]`.
3. **Title sentence** — `This report contains information about recent crimes reported in the 2D District.`
4. **One record per "line-block"** — each record is the field/value pairs for one CCN (crimes) or arrest_number (arrests). Format varies — see "Quirk #9" below.
5. **(Crime emails only) `KEY:` legend footer** — terse field-glossary text. Parser stops here.
6. **(Arrest emails) GovDelivery boilerplate** — `Reminder:` / `Disclaimer:` / `Please Note:` paragraphs *interleaved between record batches*, then a sign-off (`Metropolitan Police Department` / `Office of Communications` / social-media links / footer).

Subscribers forwarded to `mpd@hoosoluafe.resend.app`; once Resend Inbound is
configured this lands as a webhook event, gets fetched via the Resend
"Received emails" API, and feeds into the parser.

## Bug history

Each entry: what we observed → what was wrong → what fixed it.

### #1 — District regex too loose

**Observed:** A 2D crime report ingested as district `1D`.

**Cause:** The original district-extraction regex was
`\bin\s+the\s+(\d+D)\s+District\b`. The body sometimes contained a
comparison phrase like "compared to the 1D District" or had `1D` mentioned
elsewhere before the title sentence. First match won — wrong district.

**Fix:** Anchor on the actual title prose:
`recent\s+(?:crimes|arrests)\s+reported\s+in\s+the\s+(\d+D)\s+District`.
Only the title sentence has those exact words.

(Later superseded by reading the district from the email **subject** —
that's MPD's canonical labeling — with the body anchor as a fallback.
See `extract_district()` in `email_reports.py`.)

### #2 — Abbreviated month names

**Observed:** Most `arrest_dt` columns were `NULL` after parsing. Only May
records came through with timestamps; everything else was undated.

**Cause:** `_DATE_FORMATS` only had `%B` (full month name like `April`).
MPD's templates use `%b` (3-letter abbreviation: `Apr`). The format string
`May 2, 2026 4:38:00 PM` happened to match both forms, so the bug looked
fine in our test fixtures but failed for every other month.

**Fix:** Add `%b` variants to `_DATE_FORMATS`. Keep the `%B` variants as a
defensive fallback in case MPD ever flips back.

### #3 — Multi-line address / wrapped offense fields

**Observed:**
- Arrest popups showed `1100 New York Ave NW` instead of the full street
  + city/state/zip.
- A felony popup showed offense `Carrying a Pistol Without a License (Outside Home or Place of` — closing parenthesis missing.

**Cause:** MPD wraps long values onto continuation lines:

    Arrest Location 5028 BELT ROAD NW
    WASHINGTON, DC 20016
    UNITED STATES

The line-by-line parser only matched the first line as a field; subsequent
lines didn't start with a known label, so they were silently dropped.

**Fix:** Introduce continuation handling — when a non-label line is seen,
append it to the most recent field's value. **Critical caveat — see #4.**

### #4 — Continuation logic glued footer paragraphs onto `officer`

**Observed:** Most-recent arrest in each digest had its officer field set
to the *entire* email signature: `Gilligan 13067 Reminder: Arrests do not
constitute guilt... Disclaimer: This listing may contain duplicate
records... Please Note: ...` etc.

**Cause:** After the continuation fix in #3, every non-label line now
appended to the previous field. Arrest emails don't have a `KEY:` footer
— they trail off into the GovDelivery boilerplate. Without an explicit
terminator, the parser kept "continuing" the last record's officer field
through the entire signature.

**Fix:** Restrict continuation to fields that actually wrap in MPD's
templates: `arrest_location`, `block`, `offense`, `method`. After single-
line fields like `officer`, the continuation pointer resets to `None`, so
any stray non-label line is silently ignored. See `_CONTINUABLE_FIELDS`.

### #5 — `KEY:` / `Reminder:` / `Disclaimer:` are MID-EMAIL, not end-of-records

**Observed:** Crime emails parsed only ~3 records when the actual email
contained 10+. Same `+0 / ~3` count across 30+ historical emails (a
suspicious red flag).

**Cause:** Initially I treated `Reminder:` / `Disclaimer:` / `Please Note:`
as parser terminators — assuming they appeared at the end of the email
like `KEY:`. But MPD interleaves these paragraphs **between record
batches**:

    PSA 603 ... <record 3 fields>
    
    Reminder:  Arrests do not constitute guilt...
    Disclaimer: This listing may contain duplicate records...
    Please Note: On 1/10/2019, MPD realigned police district boundaries.
    
    Arrest Number# 022608806     <-- record 4 starts AFTER the boilerplate
    ...

So terminating on `Reminder:` killed the loop after the first 3 records.

**Fix:** `_FOOTER_RE` matches only `KEY:` (the real terminator in crime
emails). Mid-email boilerplate paragraphs aren't terminators — they're just
non-label lines and the `_CONTINUABLE_FIELDS` rule (#4) keeps them from
being appended to the previous record's last field.

### #6 — Field label case collision: `OFFENSE` vs `Offense`

**Observed:** Every arrest popup was missing the offense field. Title fell
back to "Misdemeanor arrest" / "Felony arrest" — no charge listed.

**Cause:** Crime fields use UPPERCASE labels (`OFFENSE`, `BLOCK`, `LOCATION`)
and arrest fields use Mixed Case labels (`Offense`, `Arrest Location`,
`Officer`). The label scanner originally tried *every* known label and
picked the longest match. Both `OFFENSE` and `Offense` are 7 characters,
so the tie went to the first one in the iteration order — the crime label
— even when parsing an arrest email. The crime label's canonical key
(`offense`, lowercased) ended up as the dict key, but the *arrest* parser's
`field_map` only knew about the arrest label, so it dropped the value at
re-key time.

**Fix:** Make label matching kind-aware. Pass the field list explicitly
into `_iter_record_blocks` and `_split_label`. When parsing a crime email,
only check crime labels; ditto arrests. No more cross-collisions.

### #7 — Address tail noise (`WASHINGTON, DC <zip> UNITED STATES`)

**Observed:** Every arrest popup showed `1219 Connecticut Avenue NW
Washington, Dc 20036 United States` (note the broken `Dc` — `humanize_address`
title-cased the state code).

**Cause:** Cosmetic; MPD includes the city + state + country on every
address. We don't need it — every record is in DC by definition.

**Fix:** `clean_arrest_location()` strips the trailing
`WASHINGTON, DC <zip> UNITED STATES` block, keeps just `<street>, <zip>`.
Falls back to bare-street if the tail isn't present (e.g. for intersection
addresses).

### #8 — Malformed address tails (`WASHINGTON, 2 DC`)

**Observed:** One arrest leaked through with `1101 NEW YORK AVE NW
WASHINGTON, 2 DC` after #7's cleanup pass.

**Cause:** A typo in MPD's source data — the zip got mangled into the
state position. Our regex required `WASHINGTON, DC <zip>` in that exact
order; it didn't match the malformed variant.

**Fix:** Make `_ADDR_TRAILING_NOISE_RE` greedy — strip everything from
`WASHINGTON` to end-of-string regardless of what follows. We lose nothing
useful (the address has no zip in these cases anyway).

### #9 — Single-line packed record format

**Observed:** Recent crime emails (May 2026 onwards) parsed **0 records**.
Diagnostic showed:

    PSA 603 CCN 26059195 RPT DATE May 3, 2026 9:35:53 PM OFFENSE Theft METHOD Theft (Second Degree) BLOCK 100 BLOCK OF KENILWORTH AVENUE NE LOCATION Residence/Home START DT May 3, 2026 3:25:00 PM END DT May 3, 2026 4:09:00 PM

Every field of a record on a single line, separated by spaces. The previous
fixture-based test format had each field on its own line. The parser
treated the whole thing as `psa = 603 CCN 26059195 RPT DATE...` — one
record, one field, value = the rest of the line.

**Cause:** MPD changed the email template at some point in spring 2026 to
pack records onto single lines. Older emails (which we used as fixtures)
had each field on its own line. Both formats look superficially similar —
identical labels, identical content — and our test data didn't catch the
shift.

**Fix:** Add `_normalize_body()` as a pre-pass before `_iter_record_blocks`
runs the line-by-line loop. The normalizer scans the text for any known
label that appears mid-line (preceded by a non-whitespace char) and injects
a newline before it. Both single-line and multi-line variants reduce to
the same line-per-field shape.

Idempotent — labels that are already at the start of a line are left
alone, so multi-line emails (still used for arrests sometimes) work
unchanged.

## How to debug "the parser doesn't seem to work right"

The fastest path is to fetch a recent email from Resend and pipe it
through the parser on the server:

```bash
cd /root/wswdy
.venv/bin/python -c "
import asyncio
from wswdy.clients.resend_inbound import list_received_emails, get_received_email
from wswdy.email_reports import parse_crime_email, parse_arrest_email
from wswdy.config import get_settings

async def main():
    s = get_settings()
    page = await list_received_emails(api_key=s.resend_api_key, limit=20)
    for item in page['data']:
        if 'Crime Report' in (item.get('subject') or ''):  # or 'Arrest Report'
            print(item['subject'], item['id'])
            email = await get_received_email(item['id'], api_key=s.resend_api_key)
            text = email.get('text') or ''
            print('body length:', len(text))
            print('first 500 chars:', repr(text[:500]))
            recs = parse_crime_email(subject=item['subject'], text_body=text)
            print(f'parsed {len(recs)} records')
            if recs:
                print('first record:', recs[0])
            break

asyncio.run(main())
"
```

Look for:
- **0 records parsed** when the body looks valid → format change (see #9 for the canonical fix).
- **N records parsed but field X is wrong** → check the field's label name in `_CRIME_FIELDS` / `_ARREST_FIELDS`. MPD occasionally renames labels.
- **Wrong district** → check that the email subject's `for XD` substring still matches `_SUBJECT_DISTRICT_RE`.
- **Bad date** → add a new format string to `_DATE_FORMATS`.

## How to backfill after a parser fix

After deploying the fix, every email Resend has cached on its end can be
re-processed without re-forwarding from Gmail:

```bash
.venv/bin/python scripts/backfill_emails.py --subject "Crime Report"
.venv/bin/python scripts/backfill_emails.py --subject "Arrest Report"
```

The ingest is upsert-by-key (CCN for crimes, arrest_number for arrests),
so re-running over the same email is safe — already-ingested rows just
get their fields refreshed with the now-correct parse.

## Future-proofing

When you change the parser, **always**:

1. Add a regression test in `tests/test_email_reports.py` using the actual
   raw text body that broke things (paste the `repr()` output from the
   diagnostic script above, escapes and all).
2. Run the existing test suite — many of these bugs are interconnected,
   and older fixtures still encode invariants.
3. After deploy, run `scripts/backfill_emails.py` to re-process anything
   ingested under the broken parser.
